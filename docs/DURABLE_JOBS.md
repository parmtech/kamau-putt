# Durable job outbox foundation

Migration `008_durable_jobs.mysql.sql` adds a persistent outbox tied one-to-one to a reserved spend. Migration `009_durable_job_dispatch_attempt.mysql.sql` adds durable dispatch-attempt state. The queue stores action type and an opaque payload reference; payload bodies and credentials stay outside it. Duplicate job keys, reservations and dispatch-attempt IDs are rejected.

## State and safety rules

- `queued` jobs are eligible only while the owner stop is clear, operating mode is Growth, and the reservation authorization epoch still matches.
- A worker claim creates one 30-second lease and a stable provider idempotency key. Dispatch rechecks and locks the lease and reserved spend, validates operating mode and dispatch epoch, records a unique `dispatching` attempt, resets its expiry to a 30-second attempt deadline, and commits. The core checks this deadline again before invoking the adapter; the adapter must check once more immediately before sending and set its transport timeout below the remaining time. An unstarted expired lease is canceled and its reservation released. Each job has at most one provider attempt; expired in-flight attempts become `uncertain`, keep their reservation and are never automatically retried.
- Provider I/O runs outside the DB transaction. The result is settled in a second short transaction against that exact attempt ID; known accepted results still settle correctly if STOP happened while I/O was in flight. The deadline reduces false uncertainty from a delayed worker claim, but cannot forcibly stop arbitrary callback code once it has been invoked; real adapters must enforce it.
- A provider `accepted` result commits the reservation and posts its ledger entry in the same transaction as job completion. `no_effect` releases the reservation and fails the job. `unknown` marks both reservation and job uncertain; funds remain reserved.
- If the process dies after a provider may have accepted a request but before DB settlement, the attempt expires into `uncertain`; its durable attempt ID and stable idempotency key support later reconciliation without an automatic duplicate call. A late known result for that exact attempt can still settle once.
- STOP advances the epoch, cancels queued and leased-but-unstarted work and releases its still-reserved funds, and marks `dispatching` work `cancel_requested` while retaining its reservation. STOP fences later attempts and returns without waiting for provider I/O. An already-authorized attempt may still complete externally; the UI reports it as open work until its result is stored or it becomes uncertain. STOP cannot recall a request already sent to a provider. Resume never requeues canceled work; a new reservation and job intent are required.
- Job lifecycle events use a global SHA-256 chain over canonical JSON details; this avoids database JSON object-key reordering changing the verified hash. SQL triggers reject event updates/deletes. State rows are mutable projections; their audit event stream is the evidence source.

## Encrypted payload storage (migration 010)

Durable intent payloads are stored separately from queue metadata in `kp_job_payloads`. `PdoJobPayloadStore` accepts a non-empty JSON object up to 64 KiB, encrypts it with libsodium secretbox using a per-reference key derived from a separately provisioned 32-byte master key, and returns a random UUID reference. Binding the derived key to the reference prevents ciphertext from being swapped between rows. A database trigger prevents in-place payload updates. `PdoDurableJobs::enqueue` now refuses a reference that is not already present in this encrypted store and serializes enqueue under the finance-control row so a payload can be bound to only one job. The queue/audit tables continue to contain only the opaque reference, never prompt or request fields.

The worker must load the payload by reference only after it has claimed and authorized the job; adapters must avoid logging it and must clear plaintext promptly. Authentication/decryption failures are fail-closed. Payload purge is allowed only after a linked job is in a known terminal state (`completed`, `failed`, or `canceled`); uncertain work is retained for reconciliation. Key provisioning/rotation, per-field data classification/redaction, retention periods, deletion audit and production key custody are not implemented. This payload store does not make any provider call or enable a worker.

## Provider HTTP boundary (offline only)

`JsonProviderAdapter` and `CurlJsonTransport` provide a provider-neutral boundary. The adapter requires a configured exact-host allowlist and fixed HTTPS endpoint on port 443; it rejects IP literals and local/reserved hostnames, has an explicit `enabled` flag that defaults to `false`, caps JSON request/response sizes, disables redirects, and limits transport time to less than the durable attempt deadline. The cURL transport rechecks the deadline immediately before starting I/O. It sends the outbox's stable idempotency key and accepts only normalized `accepted`, `no_effect`, or `unknown` outcomes; non-2xx responses remain `unknown`. Generic response parsers cannot declare `no_effect`; that result is only returned when the transport confirms expiry before request start. Malformed responses and transport failures throw so the durable dispatcher holds funds as uncertain.

The adapter and one-shot worker are wired together in code, but no provider-specific request/response contract exists and the worker is disabled by default. Offline fake-transport cases test adapter policy only; they do not exercise cURL/TLS, send network traffic or prove a provider's idempotency semantics. Keep the worker disabled until its configured path passes MySQL and race tests, uses a reviewed provider contract, enforces per-action policy and has an audited reconciliation path.

## One-shot worker orchestration

`DurableJobWorker::runOnce()` connects the existing claim/dispatch boundary to an action-type route map containing an adapter, owner-approved credential ID and data-class allowlist. The worker is disabled by default and returns before claiming anything unless explicitly enabled, at least one route adapter is enabled, and a trusted deterministic execution-authorizer is supplied. A prior review found the dispatcher omitted the locked reservation amount when rebuilding callback context; commit `9744c7bea74eacc672cb1431ade9c6cd76247bc0` forwards those cents, and MySQL 8.4 run `40428565026` passes the new exact-amount assertion (durable-job suite 42 cases). The worker loads the encrypted payload, rejects disallowed/missing data class before opening a credential, and requires the authorizer to approve attempt and payload before resolving the active vault credential and calling the adapter; it returns only job/result metadata. Failures before adapter execution are treated as known no-effect; exceptions after adapter execution begins stay ambiguous and preserve the reservation.

Worker tests cover the default-disabled and missing-authorizer gates; direct authorizer/adapter tests cover policy and model/output/content binding. A configured-worker integration now passes **8/8** on a fresh disposable MariaDB 11.4.13 database using a synthetic owner, an owner-activated synthetic credential, a versioned synthetic offer and fake HTTP transport. It exercises exact reserved-cents propagation, selected model/output cap/idempotency, no database transaction during provider I/O, successful exact-attempt settlement, cost above reservation denial and revoked-credential denial. The suite is added to the disposable MySQL 8.4 CI matrix; that new matrix job has not yet completed. No actual verified live quote, provider contract or production policy is configured. The configured path has not been exercised with cURL/TLS, a real provider or a supervised process. Before enabling it, pass MySQL 8.4 CI and add concurrency/crash tests, provider-specific evidence for response classification and idempotency, reconciliation controls, monitoring and an owner-reviewed operational enablement gate.

## Boundaries

The queue currently has no scheduler process, supervised worker, provider-specific API contract, HTTP job API or operational reconciliation tool. The one-shot worker and HTTP adapter are connected in code but have not passed configured MySQL integration and no concrete authorization policy exists. No real job dispatch is enabled. A DB epoch cannot undo a provider action already sent. Before staging, add independent-process race/crash tests, external idempotency-contract checks, safe worker integration, supervision, metrics and tested recovery procedures.
